深度测评：WorkBuddy、豆包工作、Claude、Codex 怎么选

先判断你的工作发生在办公现场还是工程现场，再选择合适的 Agent，不必追逐一张脱离场景的模型榜单。

嘿，我是 小虎哥 ，陪伴你成为「 AI时代 有产阶层 」。

别急着选 AI 工具：四款 Agent 真正差在哪？

先讲两个任务。

第一个任务是：把电脑里 30 个文件整理一下，提取重点，做成一份汇报材料。

第二个任务是：把一个现有项目改好，修掉几个问题，再跑一遍测试。

这两个任务，你都可以交给 AI，说一句：

“帮我完成。”

但是你很快就会发现，它们根本不是一回事。

第一个任务，最重要的是 AI 能不能找到文件、读懂资料、整理格式、生成 Word 或 PPT，还要少漏内容。

第二个任务，最重要的是 AI 能不能理解一堆相互关联的文件，知道该改哪里，能不能运行命令、看懂报错，再把问题修回去。

同样是“让 AI 干活”，前者更像办公助理，后者更像工程师。

这正是最近 WorkBuddy、豆包工作、Claude Code 和 Codex 争论很多，却又经常争不清楚的原因。

大家表面上在比模型，实际上是在比四种不同的工作方式。

💬

这篇文章只讲一个判断

==别问谁更强，先问你的工作发生在哪里。==

这张图先给你一个总览。价格看每月低、中、高三个使用档位，网络看中国大陆用户的直连、登录和支付摩擦，性能分开看办公交付和工程闭环，工具接入则区分“官方连接器”与“理论上可以通过 MCP 接入”。

图里的分数不是厂商发布的榜单，也不是在同一台电脑上跑出来的统一 benchmark。因为四款工具的工作对象不同，我用 5 分制做方向性参考：办公任务看资料、格式和跨应用交付；工程任务看项目理解、修改、测试和继续修复。你不用把 4.5 和 4.0 当成数学上精确的差距，它真正要表达的是： Claude Code 和 Codex 在工程闭环上更强，WorkBuddy 和豆包工作在中文办公现场更顺手。

你如果只做文档、表格、PPT和电脑上的重复工作，最适合你的工具，未必是程序员圈里最火的那个。

你如果要改真实项目、跑测试、处理代码和数据，能聊天、能生成一个看起来不错的页面，也不等于它能替你完成工程任务。

那这四款工具到底分别多了什么、少了什么？

我来帮你把这件事掰开揉碎。

一、你以为在比较四个 AI，其实是在选择四个工作现场

我们先把一个技术词翻译成人话。

所谓 Agent，简单说，就是不只回答你，而是能接过一个目标，自己去找资料、调用工具、修改文件，最后交付一个结果。

它和聊天机器人的差别，有点像“咨询朋友”和“雇一个人干活”。

你问朋友：“这个报告怎么写？”朋友会告诉你一些想法。

你交代给一个能干活的同事：“把这批资料整理成汇报，引用保留，输出成 PPT，明天下午给我初稿。”他就需要自己找文件、做判断、反复修改，最后把文件放到你指定的位置。

AI Agent 的价值，发生在后半段。

WorkBuddy 的官方产品介绍，明确把它放在“全场景职场 AI 智能体桌面工作台”的位置上。它支持自然语言下达任务、本地文件操作、文档、表格、PPT、内容创作、数据分析、行业调研、多 Agent 并行、模型切换、MCP 和 Skills。WorkBuddy 官方产品介绍

豆包工作走的是相近方向，但入口更贴近国内用户熟悉的电脑、浏览器、Office、飞书和多模态内容。它不只想回答“怎么做”，而是想把搜索、文件、文档、表格、幻灯片、图片和视频串成一个工作任务。豆包 App Store 产品说明

你会发现，国产工具真正多出来的东西，并不是一句“中文更好用”这么简单。

它们是在争夺你原来工作的入口。

你的文件在哪里？你的表格在哪里？你的会议资料在哪里？你的团队协作在哪里？你的 PPT 最后要交给谁？

这些问题如果都发生在本地电脑、Office、飞书和中文办公流程里，那么工具离现场越近，你越容易把它用起来。

这就像在家附近找一家餐厅。

菜做得好当然重要，但它离你 50 米还是 50 公里，也会改变你最后去不去。

你肯定要说了：那 Claude Code 和 Codex 不也是 Agent 吗？

当然是。

只是它们默认进入的现场不同。

Claude Code 的官方定义非常明确：它是一个面向代码库的 Agent，能够读取代码、编辑文件、运行命令，并连接开发工具；工作入口包括终端、IDE、桌面端和网页。Claude Code 官方概览

这意味着它面对的不是“这一段文字怎么写”，而是“这个项目由哪些文件组成，哪里出了问题，改动之后有没有破坏别的功能”。

Codex 的边界正在变宽。OpenAI 当前的工作场景介绍，已经把研究、信息综合、报告、演示、日常自动化和周期性任务放在 Codex 的使用范围里，同时保留代码工程能力。Codex for work

所以，Codex 更像是从工程 Agent 继续向知识工作台扩展。

这四款工具的第一层差别，就这样出现了：

国产工具更靠近“我电脑上的工作”；Claude Code 更靠近“我的代码项目”；Codex 介于工程项目、研究资料和可审核的工作任务之间。

真正的选择，不是先问谁的模型更大，而是先问： 你的结果最后落在哪里？

图：同一个 Agent，放在办公资料和代码项目里，评价标准会完全不同。

二、WorkBuddy 和豆包工作：它们多了什么，又少了什么

它们多了一个普通人可以直接进入的工作台

以前我们使用 AI，往往要先做一件很累的事：把资料找出来，复制进去，告诉它背景，再把结果复制回 Word 或表格。

这就像每次请同事帮忙，都要先把办公室里的文件搬到会议室，开完会再搬回来。

WorkBuddy 和豆包工作想解决的，正是这段来回搬运。

WorkBuddy 的官方文档里，除了文件、文档、表格和 PPT，还专门写到资料库、权限、多人多 Agent 协作。文档修订可以先以建议形式呈现，接受之后再写回正文；HTML 内容则可以即时编辑。WorkBuddy 多人多 Agent 协作

这件事看起来不如“模型有多聪明”刺激，但它非常重要。

因为真正的办公任务，通常不是生成一次答案，而是围绕一批材料不断修改。

一份周报可能要结合会议纪要、销售表格、上周版本和领导的新要求。

一份 PPT 可能要经过三轮改稿，不能 AI 每次都从空白开始。

一个团队共用的资料库，也不能每个人都随便覆盖别人的内容。

你看，办公 Agent 的核心，不只是“会写”，而是“能不能在真实资料里工作”。

这里再把一个企业选择问题说透。

如果你的企业主要使用飞书，豆包工作的优势会被放大。文件、文档、表格、会议、任务和沟通本来就在同一套办公体系里，AI 少走几步，员工就少做几次复制粘贴。

如果你的企业主要使用企业微信、腾讯会议、腾讯文档和腾讯网盘，WorkBuddy 的优势会更明显。WorkBuddy 官方连接器文档已经列出腾讯文档、腾讯会议、腾讯网盘、QQ 邮箱、腾讯乐享和 TAPD，也支持自定义连接器；官方还提供了飞书接入指南。WorkBuddy 连接器文档

所以这句话可以说得更准确： 企业使用飞书时，豆包工作更顺着飞书入口；企业使用企业微信和腾讯办公服务时，WorkBuddy 的官方连接器更有现实优势。 这不是给国产工具贴一个“全面领先”的标签，而是承认办公软件的入口，本身就是生产力的一部分。

企业选 Agent，先看员工每天打开的办公入口，再看模型排名。

豆包工作的增量则更明显地体现在中文用户熟悉的办公链路上。

但从产品方向看，信息已经很清楚了：豆包工作不是只想成为一个更会聊天的豆包，它想成为一个能够接住中文职场待办的数字同事。

这对普通人有什么意义？

意义就是，你 不需要一开始就理解终端、代码库、Git 或 API。

你可以先从自己的真实工作开始：整理一个文件夹，合并几张表，做一份会议纪要，生成一版汇报材料，或者把一个网页任务交给它试试。

这个入口非常重要。

很多人不是不想用 AI，而是第一步就被工具教育了半天，最后还没干活，先学会了怎么配置工具。

但“能操作电脑”，不等于“能稳定交付工作”

你可能以为，既然 Agent 已经能点击、输入、找文件，那它就快要像真人一样了。

其实还差得远。

人人都是产品经理对豆包工作的实测，覆盖了 PPT、行业竞品报告、海报、视频、飞书任务看板和 Skill。测试显示，基础产物可以完成，飞书连接很有价值；但报告容易信息发散，历史材料整理仍然会遗漏，Skill 也还没有稳定做到把一套编辑规则持续复用。豆包工作实测

这其实非常符合当前办公 Agent 的真实状态。

它可以帮你把第一版做出来，但第一版能不能直接发给老板，是另一回事。

更早的一次豆包专业版与 Codex 对照测试，把任务放到了 C 盘清理、飞书表格复制、小红书评论抓取和小工具开发上。文章记录中， Codex 在实际电脑操作和代码工具迭代方面 更顺利 ；豆包更容易上手，但在 飞书文件定位、桌面授权和录屏 等环节出现了 失败 或卡住。36氪对照实测

你别急着拿这个结果给豆包工作判死刑。

这次测试早于豆包工作独立产品发布，豆包侧主要使用的是 2.1 Turbo，也没有做到同版本、同账号、同环境的严格对照。

它能说明的不是“谁永远更强”，而是一个更重要的事实： Agent 的性能，经常败在权限、页面、文件路径和工具连接上，而不是败在回答不会写。

你想想，真人同事为什么有时候也干不成活？

不是他不会做表，而是文件没权限、系统登不上、客户资料找不到、网页弹出了验证码。

电脑 Agent 也是一样。

所以国产工具相对 Claude Code 和 Codex 多出来的是“离普通办公现场更近”。

它们相对少的，则是面对复杂任务时那种稳定、可追溯、能持续修复的工程闭环。

三、Claude Code 和 Codex：它们多的不是一个聊天框，而是一套闭环

Claude Code 的强项：把项目当成一个整体来理解

如果你没有接触过代码项目，很容易误解 Claude Code。

你会以为它只是一个能写代码的聊天机器人。

其实代码生成只是最浅的一层。

真正有价值的地方，是它可以进入一个项目，查看文件，搜索代码，执行命令，运行测试，然后根据测试结果继续修改。

你可以把它想成一个坐在项目旁边的工程师，而不是一个只在白板上给你写示例的人。

如果你的编程工作还要接开源生态、GitHub、IDE、终端，或者要把 Obsidian 这样的本地 Markdown 知识库接进长期工作流，Claude Code 和 Codex 目前更占优势。

这里的“优势”，不是说国产工具完全接不上。WorkBuddy 同样支持 Skills、MCP 和自定义连接器，理论上也可以读取本地 Markdown 文件。差别在于，Claude Code 和 Codex 周围已经形成了更密集的开源 CLI、插件、MCP、项目模板和开发者经验，很多连接方式可以直接复用，而不是每次从头配置。

这就像两条路都能到目的地。一条路允许你自己修桥，另一条路沿途已经有很多现成的桥、路标和维修记录。对愿意折腾的人来说，前者也能走；对要把知识库、代码库和自动化流程长期维护起来的人来说，后者通常更省力。

Codex 的强项：工程能力之外，开始接住知识工作

Codex 的变化很有意思。

它早期最容易被理解成 OpenAI 的代码 Agent，但现在官方工作场景已经扩展到研究、资料综合、报告、演示和周期性任务，并强调引用、审核和用户批准。

因为不是所有人的工作都需要改代码，但很多人的工作都需要处理一堆资料，做判断，形成交付物，再经过别人审核。

比如分析一批公开资料，做一份竞品简报；把多个文件整理成结构化报告；定期生成某个主题的监测结果；或者先生成一个内部小工具，再让人检查后使用。

这些任务，已经介于办公和工程之间。

WorkBuddy 和豆包工作更像“帮你操作办公现场的人”；Claude Code 更像“进入项目内部干活的工程师”；Codex 则试图把这两种能力放进同一套可调度的工作系统里。

但你别误会，我不是在说 Codex 就自动成为普通人的最佳选择。

产品边界扩大，通常也意味着使用方式变复杂。

你需要知道资料放在哪，项目边界是什么，哪些文件允许修改，哪些结果必须审核，什么时候应该并行，什么时候应该让 Agent 停下来问你。

海外工具少了什么：不是能力，而是低摩擦的本土入口

Claude Code 和 Codex 在工程闭环上更成熟，并不代表它们没有缺点。

对于普通中国职场人来说，它们的门槛至少有三层。

第一层是工作方式门槛。

你要理解项目、文件夹、终端、权限和上下文。哪怕你不写代码，也需要知道自己到底让 AI 改了什么。

第二层是使用成本门槛。

Claude 官方价格页显示，Pro 月付 20 美元，年付折算 17 美元/月，并包含 Claude Code；Claude 与 Claude Code 共用计划用量池，长会话、模型和上下文会影响实际消耗。

第三层是中国用户的获得性门槛。

海外标价不等于你可以顺利注册、付款和长期使用。账号、支付、网络、地区政策和服务连续性，都要单独考虑。

这不是说所有中国用户都无法接触它们，而是说你不能把海外美元价格直接当成“我每月实际能稳定使用的成本”。网络、支付和服务连续性，本身就是中国用户的产品体验。

所以，Claude Code 和 Codex 多的是工程闭环，少的是很多普通人想要的“打开就能干活”。

这不是谁先进、谁落后的简单故事。

四、所谓性能，不能只看跑分，要看它怎么失败

现在最容易写错的，就是“性能对比”。

有人拿一个代码基准说 Claude Code 或 Codex 更强，有人拿一次 PPT 生成说某个国产工具更快，最后把四款工具排成一张榜单。

看起来很专业，实际很容易误导。

为什么？

因为办公任务和工程任务，根本没有同一把尺子。

整理一批文件，应该看它有没有漏掉历史资料，格式是否保留，结果是否放到了正确位置。

修改一个项目，应该看它是否改对文件，测试有没有通过，出现报错后能不能继续修复，最后有没有留下可追溯的改动。

这两种任务都叫“完成”，但完成标准完全不同。

第一层性能：它能不能把事情做出来

这是最容易被演示视频证明的一层。

WorkBuddy 能生成报告、表格和 PPT，豆包工作能处理办公资料、浏览器和飞书任务，Claude Code 能修改代码并运行命令，Codex 能处理代码、研究和报告。

官方文档和产品页，主要证明的就是这一层：能力存在，入口存在，工具可以被调用。

这一层当然有价值，但它离生产力还差一步。

就像厨师把菜端出来，不代表味道稳定，也不代表每次都能按时端出来。

第二层性能：它能不能稳定地做出来

稳定性要看重复测试。

同一份资料换一个文件名，还能不能找到？

网页多弹出一个登录框，还能不能继续？

表格里多一列合并单元格，还会不会把数字弄乱？

需求多加一句限制，它会不会忘掉前面已经确认的规则？

人人都是产品经理对豆包工作的体验里，最有价值的并不是“它完成了一个 PPT”，而是它同时暴露了报告过于发散、历史资料遗漏和 Skill 复用不稳定。

这些问题说明，办公 Agent 的下一关不是“会不会生成”，而是“能不能在约束下反复生成”。

你肯定要说了：那代码 Agent 的基准测试不是更客观吗？

相对客观，但也不能直接拿来替代你的工作体验。

SWE-Bench Mobile 研究使用 50 个真实移动软件任务、449 个经过人工验证的测试用例，对 22 个 Agent 和模型配置进行评估。论文报告中，最佳配置的任务成功率也只有 12%，并且同一个模型在不同 Agent 设计下可能出现很大差异。SWE-Bench Mobile 研究

这说明什么？

代码 Agent 的表现，不只由模型决定，还由任务拆分、上下文管理、工具面和验收方式决定。

办公 Agent 更是如此。

所以我不建议你沉迷“谁的跑分第一”。你真正应该关注的是：它失败的时候，你能不能看见；失败之后，你能不能接管；接管以后，返工成本是不是还能接受。

第三层性能：失败之后能不能恢复

这是最容易被忽略、却最接近真实生产力的一层。

一个工具第一次生成 PPT 很漂亮，但漏了三页关键数据，你要花两个小时重做，这算快吗？

一个工具改代码用了十分钟，但把另一个模块弄坏了，最后你花一天排查，这算高效吗？

一个工具能够自动点击电脑，但权限一变化就卡死，而且你不知道它卡在哪里，这算自动化吗？

你看，真正的性能不是“它跑了多久”，而是“从开始到交付，你总共花了多久”。

我更愿意把它叫作任务总成本。

它包括 AI 的执行时间，也包括你的等待时间、检查时间、返工时间和出错后的恢复时间。

这也是为什么，36氪那次豆包与 Codex 的对照测试值得参考，但不适合被当成绝对排名。它让我们看到，实际电脑操作中的权限、客户端、浏览器和 iframe，可能比模型回答本身更快决定任务成败。36氪对照实测

如果你只记住一个性能判断，我建议记住这一句：

会做，是能力；稳定地做，是产品；出错后能恢复，才接近生产力。

图：真正的性能，不是第一次演示成功，而是任务出错后还能不能回到交付状态。

五、价格不是月费，而是你完成一项工作的总成本

价格是这四款工具最容易被误读的地方。

WorkBuddy 的价格相对直观一些。

截至 2026 年 8 月 28 日，官方定价页列出了个人体验版、标准版、高级版和旗舰版；月付价格分别涉及免费、99 元、199 元和 999 元，连续包月页面显示 70 元、140 元和 700 元等档位。不同套餐还绑定不同基础积分、自动任务、项目、成员和代码补全权益。WorkBuddy 官方定价

豆包工作目前的价格信息变化更快。68 元、200 元和 500 元的连续包月档位。

Claude Code 的价格是美元订阅加用量限制。Pro 月付 20 美元，年付折算 17 美元/月，包含 Claude Code；

Codex 更不适合只写一个月费数字。当前个人计划里，Plus 是 20 美元/月，Pro 还分 100 美元和 200 美元两档，对应约 5 倍和 20 倍的用量级别；如果继续使用 Credits，实际成本还要看模型、上下文和任务规模。Codex 价格说明

这是什么意思呢？

WorkBuddy 更像“订阅加积分加自动任务数”，豆包工作更像“套餐加额度加办公入口”，Claude Code 更像“订阅加滚动用量”，Codex 更像“计划额度加模型和任务消耗”。

它们根本不是一张简单的价格表。

你真正需要计算的，是下面这个东西：

完成一项工作的总成本 = 购买费用 + 学习成本 + 等待成本 + 失败返工成本 + 登录、支付和网络成本。

图：月费只是入口，学习、权限、网络、等待和返工，都会进入最终账单。

那普通人到底该怎么选？

我建议你先看最终交付物。

如果你每天处理的是会议纪要、Word、表格、PPT、调研资料和本地文件，优先试 WorkBuddy 和豆包工作。它们更接近你的办公现场，第一步更容易走通。

如果你经常使用飞书、希望让 AI 接管一些电脑和中文协作任务，豆包工作值得试；如果你更看重本地文件、资料库、模型切换和多 Agent 办公协作，WorkBuddy 值得试。

如果你有真实代码仓库，需要修 bug、改功能、写测试、做依赖升级，Claude Code 更适合从工程现场开始。它的门槛高一点，但你得到的不是一段看起来不错的代码，而是一套围绕项目持续工作的能力。

如果你既要处理代码和文件，又要做研究、报告、网页、数据分析和多任务协作，可以试 Codex。但你要接受它的 Credits、模型和上下文规则，也要愿意理解项目、权限和审核边界。

因此真正决定结果的，可能不是某个榜单第一名，而是你手里那批资料、那套流程、那个项目，以及你愿不愿意把任务交给 AI 之后，认真验收它的结果。
